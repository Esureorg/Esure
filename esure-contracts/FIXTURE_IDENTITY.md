# Fixture Identity and Reset Behavior

Status: **implementation-independent design**. This document describes what a
future Soroban harness must record and check so that contract fixtures survive
Testnet resets safely. It does not choose an SDK, storage engine, or CI
provider, and it adds no deployment tooling.

## Why contracts differ from classic accounts

Classic Esure scenarios declare accounts with `generate: true`, so every run
creates and funds fresh keypairs. A Testnet reset therefore costs nothing: the
next run regenerates everything (see
[Testnet Reset Recovery](../esure-docs/TESTNET_RESET_RECOVERY.md#rerunning-scenarios-with-fresh-accounts)).

Soroban fixtures add state that is not regenerated by a run:

- **Uploaded WASM** is identified on-network by its hash and must be installed
  before an instance can be deployed.
- **Contract IDs** are derived from the deployer address, salt, and network ID.
  After a reset the same ID may be unassigned, or may later be assigned to a
  different deployment.
- **Contract storage** (instance, persistent, temporary entries) disappears on
  reset and may also expire through TTL before a reset.

Any reference to these values that outlives a run can become stale.

## Identity metadata

Each fixture has two kinds of identity. Only the artifact identity is stable.

### Artifact identity (stable, published by `esure-contracts`)

| Field | Example | Notes |
| --- | --- | --- |
| `fixtureId` | `conditional-payment` | Allowlisted identifier. |
| `version` | `1.0.0` | Immutable; never re-published with new bytes. |
| `wasmSha256` | `sha256:<64 hex>` | Digest of the exact WASM bytes. |
| `interfaceSha256` | `sha256:<64 hex>` | Digest of the published interface metadata. |
| `sourceRevision` | `<git commit>` | Reviewed source the artifact was built from. |

Artifact identity is network-independent and is never invalidated by a reset.

### Deployment identity (ephemeral, owned by a run)

| Field | Example | Notes |
| --- | --- | --- |
| `runId` | `<uuid>` | Owning run. |
| `networkPassphrase` | `Test SDF Network ; September 2015` | Must equal the configured Testnet passphrase. |
| `networkEpoch` | see [Reset detection](#reset-detection) | Network instance the deployment belongs to. |
| `wasmHash` | `<64 hex>` | On-network installed code hash; must match `wasmSha256`. |
| `contractId` | `C...` | Strkey contract address. |
| `deployLedger` | `123456` | Ledger sequence of the deployment transaction. |
| `deployedAt` | ISO 8601 | Ledger close time. |

Reports may include deployment identity for diagnosis. They must not include
WASM bytes, secret keys, or the deployer's signing material.

## Network binding

- A deployment identity is valid only for the `networkPassphrase` and
  `networkEpoch` it was recorded with.
- The harness reads the network passphrase from its own configuration, never
  from the scenario or the caller, matching the existing Testnet-only rule in
  [PROPOSAL.md](./PROPOSAL.md) (Security & Safety).
- A deployment identity recorded under one binding must never be used to
  invoke, read, or assert against a contract under another binding.

## Reset detection

The harness should treat a reset as detected when any of the following holds,
checked before the first network call of a run that references an earlier
deployment:

1. **Epoch change.** The harness records a `networkEpoch` derived from public
   network facts (for example the hash of an early ledger the harness can
   query, or the RPC/Horizon-reported genesis or protocol information). A
   different value means a different network instance.
2. **Ledger regression.** The latest ledger sequence is lower than a recorded
   `deployLedger`.
3. **Missing code.** The installed code for `wasmHash` is not found.
4. **Missing instance.** The contract instance entry for `contractId` is not
   found.

Conditions 3 and 4 alone can also mean storage TTL expiry rather than a reset.
The harness reports them as `fixture_stale` in either case and does not try to
distinguish further without condition 1 or 2.

Reset detection must use read-only queries and must not submit transactions.
Official status sources remain those listed in the
[runbook](../esure-docs/TESTNET_RESET_RECOVERY.md#official-network-status); the
harness must not hardcode reset dates.

## Redeployment ownership

| Situation | Owner | Action |
| --- | --- | --- |
| Run-scoped deployment (default) | The run | Deploy at run start. The deployment is discarded with the run; no redeployment step exists. |
| Stale reference detected in a run | The run | Fail the run with `fixture_stale` before any invocation. Do not redeploy silently. |
| Published scenario or docs example that names a concrete contract ID | Scenario maintainer | Not allowed. Examples must use symbolic `contract:<id>` references resolved at run time. |
| Shared, long-lived deployment (not designed yet) | `esure-contracts` maintainers | Out of scope until a separate design is approved, as noted in [PROPOSAL.md](./PROPOSAL.md#architecture). |
| Artifact digest mismatch | `esure-contracts` maintainers | Publish a new version. Never change bytes behind an existing version. |

Because the default is run-scoped deployment, a Testnet reset normally requires
no maintainer action: the next run deploys a fresh instance, the same way
classic runs generate fresh accounts.

## Validation gates for stale fixture references

These gates run in order. A failure stops the run and produces a sanitized,
explicit error rather than a negative assertion result.

| Gate | When | Check | Failure code |
| --- | --- | --- | --- |
| G1 Schema | Scenario validation, offline | Contract references are symbolic; no literal contract IDs, WASM hashes, or ledger numbers in scenario input. | `validation` |
| G2 Artifact | Before any network call | `fixtureId@version` is allowlisted and the local artifact's digest equals `wasmSha256`. | `fixture_digest_mismatch` |
| G3 Binding | Before reusing any recorded deployment | Recorded `networkPassphrase` equals configuration and recorded `networkEpoch` equals the current epoch. | `fixture_stale` |
| G4 Presence | Before invoking a recorded deployment | Code for `wasmHash` and the instance for `contractId` exist. | `fixture_stale` |
| G5 Code match | After deployment or before reuse | On-network code hash for `contractId` equals `wasmSha256`. | `fixture_digest_mismatch` |

For the default run-scoped model only G1, G2, and G5 apply, because each run
deploys its own instance. G3 and G4 apply only if a later design permits reuse
of deployments across runs.

`fixture_stale` should be reported with the `network` error category and
`retryable: true`, matching how the classic runner surfaces network failures.
`fixture_digest_mismatch` should be reported with the `validation` category and
`retryable: false`.

## Report and documentation hygiene

- Stored reports keep deployment identity as historical evidence. After a
  reset, contract IDs in old reports may no longer resolve, the same as
  transaction links described in the
  [runbook](../esure-docs/TESTNET_RESET_RECOVERY.md#preserving-offline-reports).
- Documentation and examples must not publish concrete contract IDs as if they
  were stable.
